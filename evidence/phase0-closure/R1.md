## Architect decision and final candidate

Run #8 (`36576443986`, `db99f240`) is the preserved failed evidence: the new
security gate correctly failed on RUSTSEC-2026-0316, published after the
reviewed advisory snapshot.

The Architect accepted RUSTSEC-2026-0316 (GHSA-jqpg-j7w6-42pr, wasmtime
43.0.2, low, CVSS 1.0) as a narrowly scoped Linux Phase Zero exception: the
advisory affects Wasmtime's dynamically typed `Val` API when lifting guest
values into host allocations (statically typed APIs are unaffected); Nexus
uses the core `Module`/`Linker`/`Store` path with `get_typed_func::<(), ()>`
and no component-model API; the SDK WASM sandbox is latent and unreachable
from the desktop; no patched 43.x exists (patched lines 36.0.16, 48.0.3,
49.0.1); the major migration is deferred; the acceptance lapses if that API
use or reachability changes. (The earlier "only >=48.0.3 / >=49.0.1"
wording in this file and the docs is corrected.)

Commit `b8402283bcf284af6963671f13a79092a2b59b2b` (tree
`febc4505f81bca3e1a15889afa36d778b6ab3de1`) adds exactly that ID to
`deny.toml` (11 accepted IDs) and the guard
`p0_fg_dep_wasmtime_uses_no_dynamic_component_val_api` (pinned in the final
trust-surface guard): it fails if a production source uses
`wasmtime::component`, `component::Val` or `component::Func`, if the SDK
sandbox stops using typed entry functions, if the `WasmtimeSandbox`/
`WasmAgent` latent-API needles are removed, or if the exception's reasons
change. Mutation control: a probe string `wasmtime::component::Val` in
`sdk/src/wasm_agent.rs` failed the guard; restored byte-exactly. Local: the
security gate against a freshly fetched database passed (11 accepted, no
other vulnerability, no stale exception); fmt, diff --check, clippy and the
desktop suite (445/0/5) passed.
