== assumptions not established by the model ==
- A-S1 stable completion (R5; R2's flush honesty restated for admitted storage), A-S2 4096-byte containment, A-S3 no silent loss after a successful completion, A-S4 read stability (design section 5): assumed by the model, never established by it. C31 shows A-S1 necessary.
- A-M1: on the supported ext4 profile, metadata operations become durable atomically and in issue order. The 'ordered' schedules use it and are themselves a superset of ext4 outcomes; the 'per-directory' schedules are a conservative over-approximation, not ext4 behaviour.
- Kernel semantics as documented: errseq sampling at open and reporting per open file description; flock per open file description; fifo(7) non-blocking open; clean-page reclaim regardless of open descriptors. Modelled, not tested.
- ext4 overwrite of written, unshared extents needs no allocation (qualification, D-6).
- SHA-256 collision resistance (bindings, digests, the storage identity).
- Domain A (store-uid rewriting) is outside the model's guarantees: gate G-AUTH stays open.
- CoreSim and the fixtures T1-T15 are derived by reading the source; they are not the Rust core. Conformance of the real core's journals (I9) and of the implementation's mutex linearization are left to the implementation mission.
- Interleavings are enumerated over the model's atomic steps; a step stands for one critical section of the design.
- The maintenance session is a specified future interface; no executable exists or is authorized.
- A-M2 (design section 5.1, corrected in R4): on the supported ext4 profile, as read from the Linux v6.17 sources, a directory fsync waits for the running or committing transaction and then tests the abort flag, and returns 0 untested when there is neither; a regular file's fsync waits for its inode's transaction only while it runs or commits, and otherwise returns 0 untested after its own checked cache flush; an abort lasts until the journal is closed; the next handle start turns it into emergency read-only, which every fsync returns first; a timestamp update by the file's owner starts a handle. Read from the sources, not tested; the runtime kernel must be qualified (G-HOST).
- A-S5 (R4: the device completes every cache flush the kernel issues) is withdrawn: the Architect did not accept it as the supported-runtime contract. R5 admits only storage to which the kernel sends no cache flush (design section 5.5); C29 keeps R4's counterexample on a volatile write-back cache, which every opening refuses (C30).
- Hardware truthfulness (A-S1): the controller's report that it has no volatile write cache is true, and nothing below the completion (controller, firmware, any bridge or hypervisor) holds acknowledged data only in volatile memory. The store observes the kernel's registration of the device, never the device (design section 5.9).
- The supported profile's superblock facts (a journal at inode 8, no external journal device, no fast_commit feature) are read by root at qualification; the store uid cannot read them at runtime, and the Owner keeps them by re-qualifying after any change (design section 13.2).
- R5: the storage qualification's root-only facts (the controller's Identify data, that the host is not a virtual machine guest, the Owner's evidence for stable completion) are established by the Owner (G-HOST); the model holds them as fixture values that only the qualification reads.
- The effective option listing, the jbd2 entry names, the kernel identity and (R5) the storage attributes, identities and controller report of the model's host are fixtures in the form Linux v6.17 prints them, not host observations. They qualify no device and no host.
- JournalSim is the smallest state of the cited jbd2, ext4 and block-layer branches, not a kernel: one journal, commits one at a time in order, background commits and aborts at chosen points. R5: on admitted storage no flush is sent; on a volatile cache every flush is honoured unless a scenario fails it; on a cache the kernel registered as absent, a superblock write is taken to reach the medium before the home writes (the worst order). Its enumeration is bounded (initial states of at most four events, one background event before each activation step) and is not an exhaustive proof.
- Write-error detection rests on the device's errseq (design section 5.6): its counter has 19 bits, and a collision would need 2^19 further errors on the device, each observed through the device's own mapping by another reader, before the next tail update or metadata change. Not modelled; outside the supported failure model.
- The whole model's checkpoint covers the directory metadata durable when it runs; on a cache other than admitted storage, file data are not modelled as volatile (such storage is refused, or outside A-S1).
- One filesystem: the profile requires the PROVISION directory, the state root's parent and the state root on one filesystem, verified by st_dev. The model has one journal per world; the per-directory family over-approximates independent directories, and so independent filesystems.
- Composed scenarios are bounded: one pool file claimed, one generation of dependent work, every procedure prefix, a first crash F1 or F2 under every schedule, and a second crash F1 or F2 under every schedule. R5's C32: every prefix of first provisioning and of succession followed by F1, four hosts, five storage events and every second crash. They are not an exhaustive proof.
- The Python model is not the Rust implementation; no Cargo command or Rust test ran.
- A-S2 is load-bearing: with a 16 KiB failure unit, losing a durable ActionStarted block while the next block stays zero yields a valid shorter prefix (UnsealedAction -> UnsealedNoAction). Outside every guarantee; attested by the Owner, qualified empirically.
