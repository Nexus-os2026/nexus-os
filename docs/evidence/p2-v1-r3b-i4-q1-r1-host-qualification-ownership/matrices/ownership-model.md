# P2-V1-R3B-I4-Q1-R1: the collision qualification's ownership model

H6 qualifies one host fact: `StartTransientUnit` for the name of a loaded
transient scope is refused with exactly `org.freedesktop.systemd1.UnitExists`.
To ask that, something must hold a loaded scope that is definitely the
harness's. The repair makes no new owner for it: the scope is the one the
accepted production owner creates and proves, and the harness's only own
request can affect nothing.

## Who owns what

| Thing | Owner | Authority it gives |
|---|---|---|
| the helper | `execution::place` consumes it; from then on it is owned with its scope operation (`ScopedHelper`, or a `PlacementFailed`'s cleanup: confirmed, or one `RetainedBoundary` holding both) | its process id is a locator of the backend's own unreaped child |
| the first start (production's `StartTransientUnit`, PIDs = the helper) | the pending scope operation, from before the request is issued (`ScopeBoundary::Pending`), inside that owner | none until proven; cleanup ownership of the candidate cgroup only |
| the unit name | generated by production (`ScopeManager::prepare`) | a locator, never authority (I4-R1) |
| the proven scope | `ScopedHelper` (`ScopeBoundary::Proven`): the cgroup retained by descriptor, bound to the manager's unit by exact `Id` and `ControlGroup` | `cgroup.kill`, counters and emptiness through the descriptor; never by name |
| the probe's request (`start_without_processes`) | nothing: it carries no process and no property | none needed: it cannot place a process or change a unit (`primary/excerpts.md`) |

The harness itself (`p2q`) has no owner type, no raw helper kill or reap, no
stop path and no unit name of its own for H6 (`p2_g_11`).

## The first start: every outcome (production semantics, unchanged)

Conceptually: no native effect → the request may have an effect → one of:

| Outcome of the first start | State | What is ended, and when | The case |
|---|---|---|---|
| a delivered reply, every proof passed | definitely created and owned: `Proven` | the scope through its descriptor (`cgroup.kill`), the helper reaped only then, emptiness observed, the owner's end confirmed (`released`) | continues |
| exact `UnitExists` | definite collision, no ownership: `collided` | the foreign unit: never stopped, killed, opened or claimed; the harness's helper: killed, reaped only once the kernel shows it outside a cgroup of that name | fails (`unplaced`), cleanup confirmed |
| a timeout, a broken connection, an unexpected error, a reply that does not decode | uncertain, still owned: `Pending` | discovered and proven if the job attaches the helper (then as above); otherwise settled through the candidate cgroup, or retained: the helper killed, never reaped while unresolved | fails (`unplaced`: 3 explicit retries, then `release`: the owner's drop backstop, never a confirmation, never a reap of an unresolved helper) |
| a panic after dispatch | uncertain, still owned (caught inside `place`, never crossing it) | as the row above | fails, as above |
| a cleanup failure (a scope not observed empty) | `CleanupFailed`: a `RetainedBoundary` with what was not confirmed | nothing is confirmed without observation; a `StopUnit` reply is never proof | fails |

Carried by: `i4q1r1_nc1` (collision), `i4q1r1_nc2` (uncertain), `i4q1r1_nc3`
(panic), `i4q1r1_nc4` (proven, released, observed), all through
`execution::place` over the model; and the accepted I4/I4-R1 suite (38
behavioural controls, rerun unchanged).

## The probe's request: every outcome

The request is sent only while the proven scope holds the live helper
untouched (populated, not killed), and the scope is released only after the
answer is read and the helper is seen where the proof put it.

| Answer | Meaning | The case |
|---|---|---|
| exact `UnitExists` | refused before any property was read: no effect | asserts the binding unchanged, releases its scope through the owner, observes nothing left |
| any other error, a job (`Returned`), a timeout, a broken connection, a reply that does not decode, a panic | unknown; the request may still be handled later | fails at once; claims nothing; the proven scope is ended by its owner's drop backstop (descriptor kill; the helper may be reaped: the scope is proven and the request names no process id); any unit left under a verifier name is reported by the checked observation, never swept |

## The collision probe's safety (mission section 9)

- **The first unit's lifetime.** The production owner's proven scope,
  holding the live helper, populated and not killed, from before the request
  until its answer has been read and the helper seen unchanged; only then is
  it ended through its descriptor and observed empty.
- **Whether the second request contains a PID.** No: no `PIDs`, no
  `PIDFDs`, no property at all (`properties = []`, `aux = []`). A scope's
  processes come only from those two properties (`dbus-scope.c` 86, 142).
- **What could happen if it is processed later.** While the proven unit is
  loaded: refused (`UnitExists`) before any property is read. After the
  unit is gone: a creation attempt for a scope without processes, which
  systemd refuses when it loads it (`scope_verify`); its start job is
  refused; nothing is started and no process is attached; the unloaded unit
  and its transient file are freed. A manager that did not conform could
  only leave a unit without processes under a verifier name: reported by
  the checked observation, never swept by name.
- **What remains true if the reply times out.** The request's effect is
  unknown and may happen later; whatever it is, it cannot place a process or
  change the loaded unit. The case fails without claiming anything. The
  helper's process id is never named by the request, so reaping the proven
  scope's helper creates no reuse hazard for it.
- **Whether removal of the first unit could turn a delayed second request
  into a new creation.** Into a creation *attempt*, yes; into a creation
  that holds or receives a process, no (the bullet above).
- **No ordering assumption.** Nothing here relies on D-Bus or systemd
  handling calls in order, or on a timed-out request having disappeared:
  the request is harmless at any time, by its content.

## Residual (accepted production semantics, for the Architect)

A collision whose `UnitExists` reply is lost (a timeout, a broken
connection) is, to the backend, an uncertain start without a candidate. The
accepted settling (I4-R1, `scope/pending.rs` `reconcile`) then attempts
`StopUnit` for the operation's own generated name, never as a confirmation:
the operation stays `CleanupFailed`, its helper unreaped. In that case a
foreign unit holds the name. It requires a foreign unit already loaded under
a fresh backend-random 128-bit name. Every execution and every live scoped
case shares this; the repaired H6 inherits it from the production owner and
adds no stop path of its own. Reproduction E shows it on the model
(`reproduction/run.out`). Whether settling should ever stop a unit without a
delivered reply or a candidate is a production trust-model decision outside
this mission (no production change was made).
