== assertion and model changes (requirement preserved) ==
- C05: recorder loss is read from the exchange's latched fatal cause (WorkerLost) instead of R1's separate 'lost' flag; the requirement (loss is latched while locks stay held) is unchanged.
- C08: R1 asserted that, without the drop guard, an apply step saw no signal until a separate join-handle call. R2 makes the join-handle check part of every apply step, so the first apply latches WorkerVanished and delivers the failure: the requirement is preserved and the timing strengthened.
- C11 and C12: procedures run inside a maintenance session (R1's modelled procedures held no lock). C12 now runs under ordered and per-directory persistence schedules instead of fsync_dir-only durability; its safety assertions are unchanged; re-qualification and a valid retirement series were added.
- C15: the INV-4 assertion 'acknowledged before the failed sequence' became 'acknowledged no further than P, the durable position at the latch', which covers every fatal cause.
- C03 and C05: R1's evict (pages and inode, only with no open descriptor) became evict_inode in the same scenarios; page reclaim with open descriptors is now separate (C22).
- C10: the PROVISION grammar has a revision field; two non-canonical variants were added.
- C03: the writer's EIO is read from the exchange's latched fatal cause (Sync) instead of R1's 'failed' field; the requirement (the writer observes EIO; a new description's sync certifies nothing) is unchanged.
- C09 and C16: every restart image set now also includes page reclaim while descriptors are open (F1+page-reclaim), so their counts grew (C09 17 to 18 images, C16 25787 to 26078 images); every R1 assertion is applied to every image.
- C12: its summary counts outcomes (one per crash point after F1, and one per schedule and data choice after F2) instead of R1's crash points, and adds recovery counts.
- R3, owner startups and maintenance sessions activate before they read the store (design section 10.6). Every retained control's assertion and every retained check's detail line is identical to the R2 output, except C23's, which now also checks the R3 re-publication recovery (11 procedures and recoveries instead of 10).
- R3 model correction: the Worker's identity recheck (W5) resolved the journals directory through the world's first root; it now uses the root the owner opened, as design W5 and section 8.1 specify. Without it no owner could run on a successor root.
- R3 model correction: flock ownership was keyed by Python object identity, so a lock held when a world was cloned could never be released in the clone (a spurious Busy after F1). It is keyed by a serial of the open file description. No retained check cloned a world with a lock held.
- R4 model correction (F4): fsync_file returned EIO for every aborted, unnoticed journal. It now follows jbd2_complete_transaction: a running transaction is waited for and the abort flag tested; a completed one returns 0 untested. R3 assumed the probe's fsync always waited for the probe's transaction. No R3 check took the old branch (R3-F4-REACH), the safety requirement is unchanged (no claim on a selection whose dependencies are not durable), and the refusals it gave are now derived from the probe's handle start (C28, C29).
- R4: touch() models an abort landing between ext4's and jbd2's handle tests, and activation's hook sees the two probe windows; no retained check uses either.
- R4: every opening checks the effective profile (design section 6.4, steps 9-11) and PROVISION has a kernel field. The model's host is the qualified profile, so every retained check's result, every retained control's assertion and every retained detail line is identical to R3's output.
- R5, C28, a domain change. Old assumption: A-S5, every cache flush succeeds; the later continuations ran on a volatile cache with every flush honoured. New domain: admitted storage (stable completion, design section 5.5), to which no flush is sent; the continuations add reported home and superblock write failures, a write in flight and the R4 witness's failed flush (12 instead of 6). Retained historical counterexample: R4's checkpoint witness, re-run on the unchanged R4 model (R4-F2-WITNESS) and kept in C29 on a volatile cache. Replacement assertion: every certified dependency survives every continuation and a power loss on admitted storage. Unchanged safety requirement: no certified activation's dependency is lost in domain H. The activation runs and their counts are unchanged.
- R5, C29: R4's 'necessity of A-S5' witness is kept, with the same events, on a volatile write-back cache, and relabelled as R4's counterexample, retained (such storage is not admitted, C30); the three discarded-status cases run on a volatile cache, which is where those flushes are sent; the storage paths of design section 5.8 and the admitted-storage conformance were added. No R4 assertion was removed or weakened.
- R5 model: the fixture host's device changed from a device-mapper device (253:1, dm-1) to an NVMe partition (259:3, nvme0n1p2), because R5 refuses stacked storage (R4-FIXTURE). The profile cases edit the listing under the new name. MountEnv keeps the whole /sys/dev/block link instead of the name, and adds the storage attributes and the root-only facts. Every retained check's detail line and every retained control's assertion is identical to R4's output except C28's and C29's (above).
- R5 model: SimFS has a device, stable by default, and a checkpoint that follows JournalSim's transitions (C31 checks the two agree); on stable storage nothing a retained check reads changes.
- R5 model: JournalSim has a device (stable by default; R4's semantics are the volatile cache with native FUA), home-write outcomes, the device's errseq, the in-memory and on-medium tails and the abort's rewrite of the superblock. Its tail is the oldest transaction whose home writes have not all completed, as jbd2_journal_get_log_tail computes it; on every R4 run that gives R4's result.
- R5: PROVISION has the storage fields of design section 7.5; every opening, A4 and the claim check the storage and the opening's own admission. The model's fixture is admitted storage, so every retained check runs on it.

== assumptions not established by the model ==
- A-S1 stable completion (R5; R2's flush honesty restated for admitted storage), A-S2 4096-byte containment, A-S3 no silent loss after a successful completion, A-S4 read stability (design section 5): assumed by the model, never established by it. C31 shows A-S1 necessary.
- A-M1: on the supported ext4 profile, metadata operations become durable atomically and in issue order. The 'ordered' schedules use it and are themselves a superset of ext4 outcomes; the 'per-directory' schedules are a conservative over-approximation, not ext4 behaviour.
- Kernel semantics as documented: errseq sampling at open and reporting per open file description; flock per open file description; fifo(7) non-blocking open; clean-page reclaim regardless of open descriptors. Modelled, not tested.
- ext4 overwrite of written, unshared extents needs no allocation (qualification, D-6).
- SHA-256 collision resistance (bindings, digests, the storage identity).
- Domain A (store-uid rewriting) is outside the model's guarantees: gate G-AUTH stays open.
- CoreSim and the fixtures T1-T15 are derived by reading the source; they are not the Rust core. Conformance of the real core's journals (I9) and of the implementation's mutex linearization are left to the implementation mission.
- Interleavings are enumerated over the model's atomic steps; a step stands for one critical section of the design.
- The maintenance session is a specified future interface; no executable exists or is authorized.
- A-M2 (design section 5.1, corrected in R4): on the supported ext4 profile, as read from the Linux v6.17 sources, a directory fsync waits for the running or committing transaction and then tests the abort flag, and returns 0 untested when there is neither; a regular file's fsync waits for its inode's transaction only while it runs or commits, and otherwise returns 0 untested after its own checked cache flush; an abort lasts until the journal is closed; the next handle start turns it into emergency read-only, which every fsync returns first; a timestamp update by the file's owner starts a handle. T7. Why the R4 witness cannot lose required history on admitted storage.
Take a committed transaction T that the tail passes. By T5, every home buffer of T left the
checkpoint list unlocked and clean, so each home write had completed, or the buffer was re-logged in
a later committed transaction or freed and revoked (jbd2's own rules, not storage-dependent). Each
completed write either succeeded or failed:
- succeeded: on admitted storage the data were stable at that completion (A-S1, stable completion).
  The discarded flush at checkpoint.c:338-339 is not sent (blk-core.c:809-820) and whatever status it
  returns changes nothing. A later power loss keeps the home data.
- failed: the error was recorded (T4) before the buffer was unlocked, so before the tail was
  computed. The tail update aborts at journal.c:1861-1864, before the new tail is set; the abort's
  superblock write carries the old tail; recovery replays T from the log.
A home write still in flight at a power loss keeps T on the checkpoint list (T5), so the tail cannot
have passed T.
If the superblock write itself fails (journal.c:1827-1837), the abort rewrites the new tail
(journal.c:2592-2595). Every home write of the released transactions had already completed
successfully (otherwise 1861-1864 aborted first), so either tail on the medium recovers the history.
No model flag stands in for these steps: each is a source branch.

T8. The same events on a volatile write-back cache (not admitted), kept separate.
(a) The checkpoint flush fails; its status is discarded (checkpoint.c:338-339). With FUA passed down
    natively (blk-flush.c:22-23, 398-403), the superblock write is stable at completion while the
    home writes may still be only in the cache: the tail has moved, and a power loss before a later
    successful flush loses committed metadata. Nothing reports it. (R4's witness, reproduced on the
    unchanged R4 model in section 1 of validation.txt.)
(b) A checked superblock-write failure (journal.c:1827-1837): the journal aborts and the in-memory
    tail stays (journal.c:1069-1071), but the abort's errno write carries the new tail
    (journal.c:2592-2595). If that write succeeds while the home writes are still only in the cache,
    a power loss can still lose the history. Detected (aborted), not prevented.
(c) Native FUA: as (a); the superblock is stable at completion, the home data are not.
(d) Emulated FUA (no BLK_FEAT_FUA): the superblock write is followed by a flush (blk-flush.c:25-26,
    401-402, 437-446, writeback_cache_control.rst:92-95). If that flush succeeds, every write
    completed before it is stable (writeback_cache_control.rst:23-27), the home writes included: no
    loss. If it fails, the request ends with the error (blk-flush.c:160-163, 182-192) and (b) applies.
(e) A later successful flush before the power loss (the next commit record's PREFLUSH,
    commit.c:152-154; fsync's flush, fsync.c:166-170): every write completed before it is stable; no
    loss.
These outcomes differ; none is claimed to equal another. The R5 model's JournalSim runs each of them
(check C31) without inventing an abort at an unchecked site.

- Whether the controller's report of no volatile write cache is true, and whether anything below

- Found by that reading:
  * queue/write_cache is the kernel's view: a write to it sets or clears BLK_FLAG_WRITE_CACHE_DISABLED
    only (blk-sysfs.c:459-478), so "write through" alone cannot tell a device without a cache from a
    cache whose flushes were disabled; queue/fua tells them apart for NVMe (nvme/core.c:2395-2398,
    blk-settings.c:468-469).
  * After a failed superblock tail write, the abort's errno write carries the new tail
    (journal.c:1871-1872, journal.c:2592-2595): on a volatile cache a checked failure is detected but
    does not prevent the loss.
  * jbd2_journal_get_write_access aborts the journal at the first metadata change after a recorded
    write error, whatever ext4's errors= option (transaction.c:1222-1232).
  * errseq's own comment bounds its detection (errseq.c:22-23).
  * ext4's file data complete through ext4's bio completion (page-io.c), not buffer.c's; the design
    first cited buffer.c for both and was corrected before any run.
