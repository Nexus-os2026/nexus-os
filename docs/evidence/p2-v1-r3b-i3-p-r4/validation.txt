- Kernel semantics as documented: errseq sampling at open and reporting per open file description; flock per open file description; fifo(7) non-blocking open; clean-page reclaim regardless of open descriptors. Modelled, not tested.
- ext4 overwrite of written, unshared extents needs no allocation (qualification, D-6).
- SHA-256 collision resistance (bindings, digests).
- Domain A (store-uid rewriting) is outside the model's guarantees: gate G-AUTH stays open.
- CoreSim and the fixtures T1-T15 are derived by reading the source; they are not the Rust core. Conformance of the real core's journals (I9) and of the implementation's mutex linearization are left to the implementation mission.
- Interleavings are enumerated over the model's atomic steps; a step stands for one critical section of the design.
- The maintenance session is a specified future interface; no executable exists or is authorized.
- A-M2 (design section 5.1, corrected in R4): on the supported ext4 profile, as read from the Linux v6.17 sources, a directory fsync waits for the running or committing transaction and then tests the abort flag, and returns 0 untested when there is neither; a regular file's fsync waits for its inode's transaction only while it runs or commits, and otherwise returns 0 untested after its own checked cache flush; an abort lasts until the journal is closed; the next handle start turns it into emergency read-only, which every fsync returns first; a timestamp update by the file's owner starts a handle. Read from the sources, not tested; the runtime kernel must be qualified (G-HOST).
- A-S5 (new in R4): the device completes every cache flush the kernel issues; a failed flush is a storage fault outside domain H. v6.17 discards the status of the flush before the log tail moves (checkpoint.c:338-339); C29 shows that such a failure can lose a certified dependency with no error reported to any process. Assumed, not established.
- The supported profile's superblock facts (a journal at inode 8, no external journal device, no fast_commit feature) are read by root at qualification; the store uid cannot read them at runtime, and the Owner keeps them by re-qualifying after any change (design section 13.2).
- The effective option listing, the jbd2 entry names and the kernel identity of the model's host are fixtures in the form Linux v6.17 prints them, not host observations.
- JournalSim is the smallest state of the cited jbd2 and ext4 branches, not a kernel: one journal, commits one at a time in order, background commits and aborts at chosen points, every flush honoured unless a scenario fails it. Its enumeration is bounded (initial states of at most four events, one background event before each activation step) and is not an exhaustive proof.
- One filesystem: the profile requires the PROVISION directory, the state root's parent and the state root on one filesystem, verified by st_dev. The model has one journal per world; the per-directory family over-approximates independent directories, and so independent filesystems.
- Composed scenarios are bounded: one pool file claimed, one generation of dependent work, every procedure prefix, a first crash F1 or F2 under every schedule, and a second crash F1 or F2 under every schedule. They are not an exhaustive proof.
- The Python model is not the Rust implementation; no Cargo command or Rust test ran.
- A-S2 is load-bearing: with a 16 KiB failure unit, losing a durable ActionStarted block while the next block stays zero yields a valid shorter prefix (UnsealedAction -> UnsealedNoAction). Outside every guarantee; attested by the Owner, qualified empirically.
