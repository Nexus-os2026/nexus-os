======================================================================
0. PURPOSE
======================================================================

Build a complete, repository-resident development harness so that future
Codex and Claude Code sessions can determine, without depending on chat
history:

1. what permanent Nexus engineering rules apply;
2. what exact mission is currently authorized;
3. what work is and is not allowed;
4. what reusable workflow should be followed;
5. what has already been completed;
6. what evidence exists;
7. what remains unresolved;
8. what exact action may happen next;
9. where independent review begins;
10. where implementation authority ends.

The harness must support long-running missions, context compaction,
fresh sessions, Codex/Claude switching, interruption recovery,
independent Architect review, and deterministic evidence collection.

DO NOT solve this by creating another giant prompt file.

The architecture must separate:

PERMANENT POLICY
REUSABLE PROCEDURE
MISSION-SPECIFIC AUTHORITY
PROGRESS
EVIDENCE
REVIEW / HANDOVER

A writable string is never authority.

A mission file records an Architect-approved authorization envelope;
the file does not create new authority by itself.

Git state, exact candidate identity, execution receipts, required checks,
and Architect/Owner authorization remain distinct concepts.

======================================================================
9. MUTATION / CONTROL RESULT MODEL
======================================================================

The harness MUST fix the class of mistake where a wrapper expects one
stdout marker per logical control even when multiple controls are
satisfied by one deduplicated command.

Define separate result types.

Prerequisite result:

PASS
FAIL
HARNESS_ERROR
NOT_RUN

Mutation/control result:

KILLED
SURVIVED
INVALID
HARNESS_ERROR
NOT_RUN

Mission result:

RUNNING
BLOCKED
READY_FOR_REVIEW
FAILED

Do not treat:

117/117 prerequisite commands passed

as equivalent to:

183/183 mutation controls completed.

If one command satisfies multiple control IDs, receipts must contain an
explicit mapping such as:

command_execution_id
  -> [control_id_1, control_id_2, ...]

Validation must evaluate logical coverage through that mapping.

Missing duplicate stdout markers must not create a false failure if
coverage is independently proven.

Likewise, one successful prerequisite must never create false success
for mutations that were not executed.

Implement documentation and, if safe and bounded, a small deterministic
validator/test for this receipt mapping.

DO NOT rerun the Candidate 10 mutation campaign as part of this mission.
